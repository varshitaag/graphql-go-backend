# Gin + GraphQL API — Books

A production-structured **GraphQL API** built with **Go**, **Gin**, and **gqlgen**. Implements full CRUD (Create, Read, Update, Delete) for a `Book` resource using an in-memory store. Designed so every file has a clear purpose and a clear relationship to the equivalent REST concept.

## Folder structure

```
gin-graphql-api/
│
├── main.go                        ← entry point, starts the server
├── go.mod                         ← module definition + dependencies
├── gqlgen.yml                     ← code generation config (gqlgen)
├── .env.example                   ← environment variable template
├── .gitignore
│
├── config/
│   └── config.go                  ← loads env vars into a Config struct
│
├── graph/                         ← everything GraphQL lives here
│   ├── schema.graphql             ← THE API CONTRACT (types, queries, mutations)
│   ├── resolver.go                ← business logic (replaces handlers/)
│   ├── handler.go                 ← HTTP bridge: parses + executes GraphQL requests
│   ├── errors.go                  ← structured error types with machine-readable codes
│   ├── context.go                 ← per-request values stored in context.Context
│   ├── scalar.go                  ← custom scalar types (DateTime, UUID, etc.)
│   ├── resolver_test.go           ← unit + integration tests
│   └── generated/                 ← (auto-generated by gqlgen, do not edit)
│       └── generated.go
│
├── middleware/
│   ├── cors.go                    ← Cross-Origin Resource Sharing headers
│   ├── logger.go                  ← logs operation name, not just "POST /graphql"
│   └── recovery.go                ← panic recovery → GraphQL-shaped error response
│
├── models/
│   └── book.go                    ← Book + BookInput Go structs (unchanged from REST)
│
├── routes/
│   └── router.go                  ← registers ONE route: POST /api/v1/graphql
│
├── store/
│   └── book_store.go              ← thread-safe in-memory data layer (unchanged from REST)
│
└── test_graphql.sh                ← curl-based smoke test script
```

### The one rule of this structure

> **`graph/` is the GraphQL layer. Everything outside it is framework-agnostic.**

`models/` and `store/` know nothing about GraphQL or HTTP. If you wanted to add a REST API alongside the GraphQL one, you could add a `handlers/` folder and reuse `models/` and `store/` unchanged.

## Every file explained

### `main.go`
The entry point. Loads config, sets up the router, starts the server. Identical in purpose to the REST version — switching from REST to GraphQL does not change `main.go`.

---

### `config/config.go`
Reads environment variables and provides a `Config` struct to the rest of the app. Gives you a single place to see every knob the application has. Uses defaults so the app runs with zero configuration for local development.

---

### `graph/schema.graphql` ⭐ Most important file
This is the **entire API contract** in one place. It defines:

- **Types** — the shape of data (what a `Book` looks like)
- **Queries** — read operations (what the client can ask for)
- **Mutations** — write operations (what the client can change)
- **Input types** — the shape of data the client sends on writes

In REST, the API contract was implicit — spread across route declarations, handler signatures, and model structs. In GraphQL, the schema is the single source of truth. Any change to what the API accepts or returns starts here.

```graphql
type Book {
    id:        ID!       # "!" = non-null, never nil
    title:     String!
    author:    String!
    year:      Int!
    price:     Float!
    createdAt: String!
    updatedAt: String!
}

type Query {
    books:         [Book!]!    # list all books
    book(id: ID!): Book        # get one book (nullable — null if not found)
}

type Mutation {
    createBook(input: BookInput!): Book!
    updateBook(id: ID!, input: BookInput!): Book
    deleteBook(id: ID!): Boolean!
}
```

### `graph/resolver.go`
**REST equivalent: `handlers/book_handler.go`**

Contains one function per schema field in `Query` and `Mutation`. The key difference from REST handlers:

| REST handler | GraphQL resolver |
|---|---|
| Reads input from `c.Param()`, `c.ShouldBindJSON()` | Receives parsed, typed arguments directly |
| Sends response via `c.JSON(statusCode, data)` | Just returns `(value, error)` |
| Knows about HTTP status codes | Knows nothing about HTTP |
| `gin.Context` as first arg | `context.Context` as first arg |

```go
// REST handler
func (h *BookHandler) GetBook(c *gin.Context) {
    id, _ := strconv.Atoi(c.Param("id"))
    book, err := h.Store.GetByID(id)
    if err != nil {
        c.JSON(http.StatusNotFound, gin.H{"error": "not found"})
        return
    }
    c.JSON(http.StatusOK, gin.H{"data": book})
}

// GraphQL resolver — same logic, no HTTP
func (r *Resolver) Book(ctx context.Context, id string) (*models.Book, error) {
    intID, _ := strconv.Atoi(id)
    book, err := r.Store.GetByID(intID)
    if err != nil {
        return nil, nil // not found → return null to the client
    }
    return &book, nil
}
```

---

### `graph/handler.go`
**REST equivalent: the Gin router itself**

The HTTP bridge between Gin and the GraphQL engine. In REST, Gin matched each URL+verb to a handler. Here, `handler.go` receives every request at `POST /graphql`, parses the query document, and dispatches to the correct resolver.

This is the plumbing layer. In production you'd replace it with gqlgen's generated `ExecutableSchema`, which does the same thing but handles all edge cases automatically (fragments, aliases, introspection, directives, etc.).

---

### `graph/errors.go`
**REST equivalent: the ad-hoc `gin.H{"error": "..."}` calls scattered across handlers**

Centralises error construction. Every error gets a `message` (human-readable) and a `code` (machine-readable), so a React frontend can `switch (error.code)` to show the right UI.

```go
// REST — different shape in every handler
c.JSON(http.StatusNotFound, gin.H{"error": "book not found"})
c.JSON(http.StatusBadRequest, gin.H{"error": "invalid id"})

// GraphQL — consistent shape, machine-readable code
return nil, NotFound("book", id)        // { message: "book with id 5 not found", code: "NOT_FOUND" }
return nil, ValidationError("price > 0")  // { message: "...", code: "VALIDATION_ERROR" }
```

---

### `graph/context.go`
Shows how to pass per-request data (authenticated user, request ID, logger) through the call chain using `context.Context`. REST used `gin.Context.Set("key", value)`. GraphQL resolvers only receive `context.Context`, so request-scoped values live there instead.

---

### `graph/scalar.go`
Custom scalar types. GraphQL's built-in scalars are `Int`, `Float`, `String`, `Boolean`, and `ID`. Anything else (dates, UUIDs, uploaded files) needs a custom scalar defined here and declared in the schema.

---

### `graph/generated/` (auto-generated)
**Do not edit this directory.** Its contents are produced by running:
```bash
go run github.com/99designs/gqlgen generate
```
gqlgen reads `schema.graphql` and `gqlgen.yml` and generates a fully type-safe Go implementation of the GraphQL execution engine. Our hand-written `handler.go` is a simplified version of what lives here.

---

### `middleware/cors.go`
Cross-Origin Resource Sharing headers. GraphQL APIs are almost always called from a browser on a different origin (e.g. your React app on port 3000 calling the API on port 8080). Without CORS headers, the browser blocks every request before it reaches the server.

Also handles preflight `OPTIONS` requests, which browsers send before every `POST` that carries a `Content-Type` header.

---

### `middleware/logger.go`
**REST equivalent: Gin's built-in logger**

Gin's default logger would print `POST /graphql` for every single request — useless, since every operation goes through that same URL. This middleware peeks at the request body to extract the operation name before passing the request along:

```
# Gin default (REST)           # Our GraphQL logger
GET /api/v1/books    200        [GraphQL] query "books" in 1.2ms
GET /api/v1/books/1  200        [GraphQL] query "book" in 0.8ms
POST /api/v1/books   201        [GraphQL] mutation "createBook" in 2.4ms

# Gin default with GraphQL — all identical, tells you nothing
POST /graphql        200
POST /graphql        200
POST /graphql        200
```

---

### `middleware/recovery.go`
Catches panics and returns a **GraphQL-shaped** error response. This is different from REST recovery in an important way:

- **REST recovery** returns `HTTP 500` with `{"error": "internal server error"}`
- **GraphQL recovery** must return `HTTP 200` with `{"errors": [{"message": "..."}]}`

This matters because GraphQL client libraries parse the JSON body regardless of HTTP status. A 500 response with an HTML error page breaks every GraphQL client.

---

### `models/book.go`
**Unchanged from the REST project.** The Go struct definition for `Book` and `BookInput`. Neither the store nor the models know anything about GraphQL — they are pure domain types.

---

### `store/book_store.go`
**Unchanged from the REST project.** Thread-safe in-memory CRUD operations. Replace with a database-backed implementation to make the app persistent.

---

### `routes/router.go`
**REST equivalent: `routes/router.go` with 5 route registrations**

GraphQL version registers **one route** instead of five:

```go
// REST
books.GET("",      handler.GetBooks)
books.GET("/:id",  handler.GetBook)
books.POST("",     handler.CreateBook)
books.PUT("/:id",  handler.UpdateBook)
books.DELETE("/:id", handler.DeleteBook)

// GraphQL
api.POST("/graphql", gqlHandler.ServeHTTP)      // all operations
api.GET("/graphql",  serveGraphiQL)              // browser playground
```

Also adds the middleware stack: CORS → logger → recovery → handler.

---

### `gqlgen.yml`
Configuration for gqlgen code generation. Tells gqlgen where your schema is, where to write the generated code, and how to map schema types to your existing Go structs (so it reuses `models.Book` instead of generating a duplicate struct).

---

### `.env.example`
Template for environment variables. Copy to `.env` for local development. Never commit `.env` to git.

## How it differs from REST

| Concept | REST | GraphQL |
|---|---|---|
| Endpoints | 5 (`/books`, `/books/:id` × 4 verbs) | 1 (`/graphql`) |
| Routing | HTTP verb + URL path | Field name in query document |
| API contract | Implicit (read the code) | Explicit (`schema.graphql`) |
| Response shape | Fixed — server decides | Flexible — client decides |
| Over-fetching | Always returns all fields | Client requests only what it needs |
| Multiple resources | Multiple HTTP round trips | One request, multiple fields |
| Error HTTP status | 400/404/500 per operation | Always 200, errors in body |
| Self-documentation | Swagger/OpenAPI (separate tool) | Introspection (built in) |
| Versioning | `/api/v1`, `/api/v2` | Evolve schema without versioning |
| Testing handler | One test per route | One test per resolver function |

## All queries & mutations

### Read all books

```graphql
{
  books {
    id
    title
    author
    year
    price
  }
}
```

The client picks which fields to return. Omit `price` and it won't be in the response.

---

### Read one book

```graphql
{
  book(id: "1") {
    id
    title
    author
    year
    price
    createdAt
    updatedAt
  }
}
```

If the book doesn't exist, the response is `{ "data": { "book": null } }` — no error, just null. This is standard GraphQL behaviour for nullable fields.

---

### Create a book

```graphql
mutation {
  createBook(input: {
    title: "The Pragmatic Programmer"
    author: "Hunt & Thomas"
    year: 1999
    price: 42.50
  }) {
    id
    title
    createdAt
  }
}
```

The mutation returns the newly created book. Ask for only the fields you need to update your UI.

---

### Update a book

```graphql
mutation {
  updateBook(
    id: "1"
    input: {
      title: "The Pragmatic Programmer (20th Anniversary)"
      author: "Hunt & Thomas"
      year: 2019
      price: 49.99
    }
  ) {
    id
    title
    year
    price
    updatedAt
  }
}
```

---

### Delete a book

```graphql
mutation {
  deleteBook(id: "1")
}
```

Returns `true` on success. Returns an error if the book doesn't exist.

---

### Fetch multiple resources in one request

This is impossible in REST without two HTTP calls. In GraphQL, you alias multiple fields in a single request:

```graphql
{
  firstBook:  book(id: "1") { title author }
  secondBook: book(id: "2") { title author }
}
```

Response:
```json
{
  "data": {
    "firstBook":  { "title": "The Go Programming Language", "author": "Donovan & Kernighan" },
    "secondBook": { "title": "Clean Code", "author": "Robert C. Martin" }
  }
}
```

## Using variables

Inline values (hardcoded in the query string) work fine, but **variables** are the right way to pass dynamic data. They separate the query document from the data, prevent injection issues, and let clients cache query documents.

```graphql
mutation CreateBook($input: BookInput!) {
  createBook(input: $input) {
    id
    title
    price
  }
}
```

Variables JSON (sent alongside the query):
```json
{
  "input": {
    "title": "Refactoring",
    "author": "Martin Fowler",
    "year": 2018,
    "price": 47.99
  }
}
```

Full curl request:
```bash
curl -X POST http://localhost:8080/api/v1/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "mutation CreateBook($input: BookInput!) { createBook(input: $input) { id title } }",
    "variables": { "input": { "title": "Refactoring", "author": "Martin Fowler", "year": 2018, "price": 47.99 } },
    "operationName": "CreateBook"
  }'
```

## Error handling

GraphQL **always** returns HTTP 200. Errors go inside the response body in an `errors` array:

```json
{
  "data": null,
  "errors": [
    {
      "message": "price must be greater than 0, got 0.00"
    }
  ]
}
```

This is the single biggest operational difference from REST. Your monitoring, alerts, and client error handling must parse the body, not the HTTP status code.

### Types of errors in this API

| Situation | REST response | GraphQL response |
|---|---|---|
| Book not found | `404 Not Found` | `200` + `{ "data": { "book": null } }` |
| Validation failed | `400 Bad Request` | `200` + `{ "errors": [...] }` |
| Server panic | `500 Internal Error` | `200` + `{ "errors": [{ "message": "internal server error" }] }` |
| Invalid query syntax | `400 Bad Request` | `200` + `{ "errors": [...] }` |

### Partial success

GraphQL supports partial success — some fields can resolve successfully while others fail:

```json
{
  "data": {
    "firstBook":  { "title": "Go Programming" },
    "secondBook": null
  },
  "errors": [
    { "message": "book with id 9999 not found" }
  ]
}
```

## Configuration

All configuration is via environment variables. Copy `.env.example` to `.env` and adjust:

| Variable | Default | Description |
|---|---|---|
| `PORT` | `8080` | Server listen port |
| `APP_ENV` | `development` | `development` or `production` |
| `GQL_PLAYGROUND` | `true` | Enable GraphiQL browser UI |
| `GQL_MAX_DEPTH` | `10` | Max query nesting depth |
| `GQL_MAX_COMPLEXITY` | `100` | Max query complexity score |
| `CORS_ORIGINS` | `*` | Allowed origins (comma-separated) |

In production, set `APP_ENV=production` and `GQL_PLAYGROUND=false` to disable the GraphiQL UI.

## Code generation with gqlgen

The `graph/handler.go` in this project is a hand-written, educational version of what gqlgen generates. In a real project you'd use gqlgen to generate the execution engine automatically.

### How it works

1. You write `graph/schema.graphql` (the schema)
2. You run `go run github.com/99designs/gqlgen generate`
3. gqlgen writes `graph/generated/generated.go` (the engine — never touch this)
4. gqlgen writes `graph/model/models_gen.go` (Go structs for your schema types)
5. gqlgen generates stub resolver files — you fill in the business logic
6. When you change the schema, re-run generate to keep everything in sync

```bash
# one-time setup: add gqlgen to tools.go
go get github.com/99designs/gqlgen

# generate (run this every time schema.graphql changes)
go run github.com/99designs/gqlgen generate
```

`gqlgen.yml` tells the generator to bind schema types to your existing `models.Book` struct (via `autobind`) so it doesn't generate a duplicate struct.

## What to add next

### 1. Real database (Postgres)

Replace `store/book_store.go` with a Postgres-backed implementation using `database/sql` or GORM. The resolver functions don't change because they only call methods on the store interface.

```bash
go get github.com/jackc/pgx/v5   # recommended Postgres driver
```

### 2. Authentication (JWT)

Add a JWT middleware that extracts the token from the `Authorization: Bearer <token>` header, validates it, and stores the user in the context using `graph.WithAuthUser(ctx, user)`. Resolver functions check for the user via `graph.AuthUserFromContext(ctx)`.

```bash
go get github.com/golang-jwt/jwt/v5
```

### 3. DataLoader (N+1 query prevention)

If you add a `User` type and books have an `author` relation, fetching 10 books would trigger 10 separate `GetUser` calls — one per book. DataLoader batches these into a single query.

```bash
go get github.com/graph-gophers/dataloader/v7
```

### 4. Pagination

Add `limit` and `offset` (or cursor-based) pagination to the `books` query:

```graphql
type Query {
  books(limit: Int = 20, offset: Int = 0): BookConnection!
}

type BookConnection {
  nodes:      [Book!]!
  totalCount: Int!
  hasMore:    Boolean!
}
```

### 5. Subscriptions

GraphQL subscriptions push real-time updates over WebSocket. Use `github.com/99designs/gqlgen` with the subscription transport to add a `bookCreated` subscription.

```graphql
type Subscription {
  bookCreated: Book!
}
```

### 6. Query depth & complexity limiting

Prevent malicious queries like deeply nested self-referential queries from hanging the server. Middleware in `graph/handler.go` can check depth before executing:

```go
// already configured in config.go via GQL_MAX_DEPTH and GQL_MAX_COMPLEXITY
```

## GraphQL vs REST — quick reference

### Same request, different style

| Action | REST | GraphQL |
|---|---|---|
| List all books | `GET /api/v1/books` | `POST /graphql` body: `{ books { id title } }` |
| Get one book | `GET /api/v1/books/1` | `POST /graphql` body: `{ book(id: "1") { id title } }` |
| Create a book | `POST /api/v1/books` + JSON body | `POST /graphql` body: `mutation { createBook(input: {...}) { id } }` |
| Update a book | `PUT /api/v1/books/1` + JSON body | `POST /graphql` body: `mutation { updateBook(id: "1", input: {...}) { id } }` |
| Delete a book | `DELETE /api/v1/books/1` | `POST /graphql` body: `mutation { deleteBook(id: "1") }` |

### When to use GraphQL over REST

Use GraphQL when:
- You have multiple clients (web, mobile, desktop) that need different subsets of data
- Over-fetching is a problem (mobile wants less, dashboard wants more)
- You want a single, versioned, self-documenting API contract
- Your data has complex relationships (books → authors → publishers)

Stick with REST when:
- You're building a simple internal service with few consumers
- Your team is more familiar with REST tooling
- You need file uploads, streaming, or HTTP caching (REST handles these more naturally)
- You want the simplest possible setup
